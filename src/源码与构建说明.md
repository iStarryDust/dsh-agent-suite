## 三条命令

```bash
cd E:\Plugin\agent管理and重发结合版\src

node build.mjs                     # 全量：tsc 预编译 → 打包 → 校验 → 部署到 ..\agent-suite（自动备份）
```

```bash

```

部署完**要重启 dsh 宿主进程**（客户端 bundle 在启动时组合）＋ 刷新页面。

## 构建到底做了什么

每个包分两个半端，规则不同：

| 半端 | 产物 | 输入 | 为什么 |
|---|---|---|---|
| 宿主（`src/index.ts`） | `lib/index.js`（ESM） | **先 `tsc` 出 JS，再交 rolldown** | 宿主半端用了**标准装饰器**（`@Remote('…')`，来自 typert 协议）和 `using` 声明；rolldown 只认 legacy 装饰器，直接喂 TS 会把 `@Remote(...)` 原样留在产物里——**Node 根本解析不了**。tsc 会把它们降级成 `__esDecorate` / `__runInitializers`，正是 harness 产物里那套 helper |
| 浏览器（`src/client/index.ts`） | `lib/client.js`（CJS 工厂壳 + CSS） | 直接从 TS 打包 | 客户端源码里没有装饰器/`using`，不需要降级 |

宿主的外部化规则 = 该包 `package.json` 的 `dependencies ∪ peerDependencies ∪ optionalDependencies`
（真实安装会把它们放在产物旁边，重复内联会造出第二份服务类）；其余内联。
浏览器相反：**只有模块表里的名字能 `require`**，其余全部内联——`require` 了模块表答不上的名字，运行时必抛。

### 构建自带的四道闸（`build.mjs` 的 `validate()`）

1. **语法**：对每个产物跑 `node --check`，装饰器/`using` 没降级会在这里当场拦下；
2. **宿主依赖**：产物 `import` 的每个裸包名，`agent-suite\node_modules` 里必须真的有；
3. **浏览器依赖**：产物 `require(...)` 的每个名字必须在 `build/platform.mjs` 白名单里；
4. **部署后冒烟**（人工，见下）：6 个宿主半端 `import` 一遍看导出形状，客户端 bundle 在假 `window.__ModuleLoader__` 里跑一遍看 `apply/inject`。

## 4 个必须内联的 harness 模块（`vendor\harness\`）

见该目录的 `README.md`。要点：`agent-memory/remote.js`、`agent-preset-authoring/remote.js`
是 **typert 代码生成的 Remote 客户端**（RPC 方法签名变了才需要重新生成），另外两个是纯函数
（预设名字表、默认工作区常量）。它们是**构建输入**，不是本套件的源码。

## 工具链为什么单独装在 `tooling\`

`src\package.json` 是**要发出去的 bundle 清单**，里面的 5 个 `file:` 依赖各自带 `workspace:*`
协议（只对 harness 那个 pnpm workspace 有意义）。在 `src\` 根上跑任何 `pnpm install` 都会因为
解析不了 `workspace:*` 而失败，所以工具链（tsdown / lightningcss / typescript / zod / clsx / @types）
单独装进 `tooling\`，并带 `node-linker=hoisted`（普通目录结构；pnpm 的 isolated 布局会漏掉
`@types/*` 这类直接依赖的顶层链接）。

`build.mjs` 每次运行会把 `clsx / zod / @types/*` junction 到 `src\node_modules\`：
rolldown 要能从**导入方所在目录**解析到它们（客户端 bundle 会内联 `clsx` 与两个 Remote 里的 `zod`）。

## 类型与编辑器

- 每个包的 `tsconfig.json` 是**自足**的（不再 `extends ../../../tsconfig.base.client.json`）：
  `jsx: react-jsx`、`moduleResolution: bundler`、`allowImportingTsExtensions`、`noEmit`。
- 依赖 `@types/node` / `@types/react`（在 `tooling\`，被 junction 到 `src\node_modules\@types`）。
  **先跑一次 `node build.mjs` 再开编辑器**，否则 junction 还没生成。
- harness 那些 `@deepseek-ai/dsh-*` 的类型在这份树里不存在——编辑器里它们会是 `any`/红线，
  这不影响构建（构建用的是 `tsc --noCheck` 的纯代码降级 + rolldown 打包）。
- **`agent-suite\packages\*\lib\types\` 是旧版 tsc 的遗留声明**，本管线不再刷新它。
  它只服务类型引用，运行时不读；真要更新得有 harness 源码树来 `tsc -b`。

## 与上一版（用 starry-fork 构建）产物的差异

同一份源码，用本管线重建后与旧产物的**代码行级**对比结果：

| 包 | 差异 |
|---|---|
| `edit-regen` | **代码行 0 差异** |
| `client-ui-settings-agent-memory` | 仅 CSS 类名哈希 |
| `client-ui-edit-regen` | 仅 CSS 类名哈希 |
| `client-ui-agents` | CSS 哈希 + 压缩器风格（`Object.assign` 展开、`@__PURE__` 注解、`$1/$2` 重编号），无语义差异 |
| `agent-memory` | 少 6 行：`SessionId` 由**内联改为外部化**（`@deepseek-ai/dsh-session` 已补进 peerDependencies） |
| `agent-preset-authoring` | 少 850 行：`schemastery` 由**内联改为外部化**（已补进 dependencies） |

后两条是**修正**：这两个包本来就该声明这两个依赖（同套件的 `agent-memory` 就是这么写的），
以前靠内联蒙过去，增量是真安装时就会有第二份 `schemastery`/`SessionId`。

CSS 类名哈希变了（`[hash]_[local]`，lightningcss 的 hash 取自**文件名**）——本管线用
`<包名>/src/client/<文件>` 作为合成文件名，所以换机器、换目录都能复现。没有任何地方依赖旧哈希：
液态玻璃插件只用 `[class*=]` / `[class$=]` 子串匹配。

## 排错

| 现象 | 看哪里 |
|---|---|
| 插件页"等待依赖" | 那是**宿主** fiber 的 phase。客户端包的宿主半端**不许**声明浏览器服务（`slots/locale/workspaces/uiWorkspace/remote`）——2026-10-18 已踩过一次，见 `.lg-audit/edit-regen-handoff.md` |
| 页面白屏 / 插件不出现 | `node build.mjs --compare` 看产物；控制台里 `web boot: … did not activate` 才是浏览器侧的真实原因 |
| 部署后想回退 | `node build.mjs --rollback`（备份在 `agent-suite\.build-backup\<时间戳>\`，按相对路径还原） |
| 构建报 `UNRESOLVED_IMPORT` | 那个包既不在 `package.json` 里声明、也不在 vendor 里 → 补声明（推荐）或补 vendor |

## 历史上踩过的坑（保留记录）

- 旧 `agent-suite\packages\client-ui-agents\lib\types\` 里有 `BlankScreen.*` / `probe.*` 共 8 个文件，
  是更早一版构建的**孤儿**（tsc 不清目录），源码里没有，`lib/client.js` 里也 0 命中。不用管。
- 本插件目录里**没有 `vendor.mjs`**（`G:\自制dsh\备份插件\README.md` 提到的那个 `E:\Plugin\agent管理\vendor.mjs`
  随目录改名消失，G 盘备份里也没有）。profile 重装出现 `failed to import` 时得先补一个。

  （tsc 输出）当输入。本管线的 `build.mjs` 每包先跑 tsc，不存在这个坑。
